# План: слияние GitHub→GitLab + секреты + календарь + подпись

## Контекст

Проект HomeWeatherClock живёт в двух репозиториях: GitLab (origin, канон, HEAD `47ffe3a` от 18.03.2026) и публичный GitHub (устарел, HEAD `5910473` от 06.06.2024). Истории разошлись от `44470ce`: на GitHub — 7 никем не слитых коммитов (Firebase Crashlytics/Analytics, policy.html, чистка хардкод-ключей, APK-нейминг), на GitLab — 4 более новых коммита (Kotlin 2.2.21, koin 4.1.1, Kamel→Coil, SDK 36). Пробный `git merge-tree` показал 5 текстовых конфликтов + скрытые ловушки.

Попутно выяснено: приложение опубликовано в RuStore (1.0.2 от 12.04.2024, сборка с GitHub-ветки), подписано **утёкшим** в публичный репо ключом (SHA-256 `9e261c6e…`, совпадение подтверждено); локальный `prod.jks` (`10:5c:67:45…`, alias `clock`) — новый ключ, под которым нельзя публиковать до ротации подписи через ТП RuStore. Токен production-calendar зашит в опубликованный APK, сервис стал платным — календарь переводим на бесплатный федеральный xmlcalendar.ru. Решения пользователя: crashlytics берём (Firebase-проект жив), версия 1.1.0, ключи погоды — только из local.properties (в проде пусто), константы приложения — в toml, чистка истории filter-repo + force-push по обоим репо.

## Этап B — Доработки (отдельные коммиты поверх merge)

**B1. Ключи погоды через local.properties (гибрид):**
- `local.properties`: добавить `weatherApiKey=<ключ>` (+ создать `local.properties.example` с пустыми значениями — коммитится).
- `composeApp/build.gradle.kts`, блок `buildConfig`: `buildConfigField("String", "WEATHER_API_KEY", provider { "\"${ваше_значение}\"" })` — значение читается из local.properties gradle-кодом (rootProject.file("local.properties")); для jvmMain/iosMain actual получает значение, для `androidRelease` — пустая строка через `sourceSets.named("androidRelease")` (если source set не существует в текущей KMP-интеграции — fallback: `androidMain` всегда пусто, ключ на Android вводится через экран настроек, как сейчас).
- `AppSettings.kt:80`: `weatherApiKeys = BuildConfig.WEATHER_API_KEY.takeIf { it.isNotBlank() }?.let(::listOf) ?: emptyList()`.
- Desktop/iOS — ключ всегда подставляется (личные сборки, в сторы не идут).

**B2. Подпись релиза:**
- `composeApp/build.gradle.kts`: `signingConfigs.create("release")` с чтением из local.properties (`storeFile`, `storePassword`, `keyAlias`, `keyPassword`); `buildTypes.release.signingConfig` → он; при отсутствии свойств в local.properties — откат на debug-подпись (сборка не ломается).
- Текущий путь для store-обновлений до ротации — старый ключ `9e261c6e…` (сейчас лежит в `/tmp/hwc-keystore-check/keystore_copy.jks`; перенесите в безопасное место вне репо, например `~/.keystores/hwc-rustore-old.jks`, и укажите путь в local.properties). После ротации в ТП RuStore — одна строка на `prod.jks`.

**B3. Календарь на xmlcalendar.ru (федеральный, бесплатный, RU-хостинг, данные 2013–2027):**
- Новый `XmlCalendarQuery(year)` вместо `ProdCalendarQuery` (`data/remote/query/calendar/`): URL `https://xmlcalendar.ru/data/ru/{год}/calendar.json`, регион убран.
- Новый DTO `XmlCalendarDto(year, months[{month, days}])` вместо `ProductionCalendarDto`; маппер в `ProdCalendarDay`: день в списке «days» без `+` → `Weekend` (сб/вс) или `NationalHoliday` (будний, typeText пустой → в `stringForCalendar()` добавить generic-текст «праздничный день» по локали, строки в strings.xml); с `+` → `PreHoliday`; не в списке → `WorkingDay`/`Weekend` по дню недели.
- `CalendarKtorService(Impl)`, `CalendarRemoteRepository(Impl)`: сигнатуры без region.
- `CalendarUseCase.getProdCalendar()`: раскомментировать/переписать логику под федеральный источник (region=0 всегда), БД-кеш остаётся как есть (схема не меняется — колонка region всегда 0, миграция не нужна).
- Настройки: удалить пункт выбора региона (`SettingsUseCase.kt:283-312` — RussiaRegionSetting, `RussiaRegionSettingsItem.kt`, `RussiaRegions.kt`); `ProdCalendarConfig.isAvailableToShow()` (`AppSettings.kt:139`) → только `isRussia`.
- `DayType.RegionalHoliday` остаётся в sealed class (не ломает БД-маппинг), но не порождается.

## Этап C — Проверки (до любого push)

1. `./gradlew :composeApp:compileKotlinJvm` — desktop-компиляция.
2. `./gradlew :composeApp:assembleDebug :composeApp:assembleRelease` — сборка Android (заодно валидирует google-services.json и crashlytics-плагины).
3. **Проверка отсутствия ключа в release-APK** (как в аудите): `unzip -p app-release.apk classes*.dex | strings | grep <ключ>` → пусто; в debug-APК ключ есть. То же для токена prod-calendar.
4. `./gradlew :composeApp:compileKotlinIosSimulatorArm64` — iOS-компиляция.
5. `./gradlew :composeApp:run` — desktop: календарь подгружается с xmlcalendar.ru, погода с ключом из local.properties.
6. Ручная проверка пользователем: debug на планшете, затем подписанный release.
7. Merge в main (локально). Push — только после подтверждения пользователя.

## Риски

- Source set `androidRelease` может не существовать в текущей KMP-интеграции — fallback описан в B1, гарантия «нет ключа в release» проверяется п.C3 в любом случае.
- `project.pbxproj` сольётся автоматически, но Xcode-проект надо открыть и убедиться, что FirebaseCore резолвится через SPM (Package.resolved от GitHub).
- xmlcalendar.ru — единственная точка отказа календаря (сервис жив с 2013, RU-хостинг; в приложении кеш в БД смягчает).
- Обновления в RuStore до завершения ротации — только старым ключом; после ротации — только prod.jks.
